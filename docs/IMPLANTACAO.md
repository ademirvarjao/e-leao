## Publicação do frontend (GitHub Pages)

1. O workflow usa os valores públicos padrão do projeto dedicado em `src/lib/client.ts`, sem variáveis de Actions que possam apontar acidentalmente para outro projeto. Não inclua chaves secretas no frontend.
2. Ative Pages com source **GitHub Actions** e autorize `GITHUB_TOKEN` a publicar Pages. O workflow executa `npm ci`, os testes, build e fallback SPA.
3. Habilite confirmação de e-mail e configure URL de produção, URLs de preview e os redirecionamentos de recuperação em **Supabase Auth → URL Configuration**. No caso de Pages, inclua a URL do host `ademirvarjao.github.io` e o caminho `/e-leao/`; aceite também o host `*.e2b.app` enquanto estiver em desenvolvimento. Não use um redirect wildcard aberto.
4. Confirme `auth.users` e **não** desative a verificação de e-mail para facilitar convites públicos. Configure SMTP de produção se o limite de e-mails do ambiente de desenvolvimento não for suficiente.

Local: `npm ci && npm test && npm run build`. Para desenvolvimento, `npm run dev`; o painel não tem acesso anônimo. `vite.config.ts` usa base relativa para Pages e HashRouter pequeno para navegação SPA.

## Gateway Edge e integração RTC/DANFSe

### Como distinguir catálogo, gateway e motor

**Diagnóstico da instalação verificada nesta revisão:** os três repositórios `ReceitaFederal` responderam para os SHAs indicados em [ANALISE-E-ESCOPO](ANALISE-E-ESCOPO.md), e o catálogo foi reproduzido a partir das migrações oficiais. No projeto Supabase do e-Leão, Auth, REST e banco estavam saudáveis, `eleao-api` estava ativa (v3, com verificação de JWT), mas **nenhum dos quatro `RTC_*_URL` estava cadastrado**. A função instalada retorna 502 para serviço sem endereço e o frontend anterior exibia o aviso genérico da conexão. Isso impede o cálculo remoto mesmo com GitHub e Supabase disponíveis; não se infere o estado de uma instância que não foi identificada. A publicação de Pages **não** implanta Edge Functions, o SQLite ou as aplicações Java/Go.

### Conectar uma instância real

1. Hospede a versão compatível ou identifique uma instância que você está autorizado a usar. Para o [regular 1.6.1](https://github.com/ReceitaFederal/calculadora-rtc-regime-regular/tree/150cccbe414d4a5edea703e4f7a424af5aa222c7), siga o README da revisão: Java 21, gerar `calculadora/db/calculadora-pro.db` com o Flyway indicado e iniciar o JAR com perfil `offline` a partir da raiz correta. O [Simples 0.0.6](https://github.com/ReceitaFederal/calculadora-rtc-simples-nacional/tree/c5b0f01c8351c3f0d0795cc617b29d233e9f98df) é outro serviço; sua automação usa as migrações do regular. O [DANFSe 1.0.0](https://github.com/ReceitaFederal/calculadora-rtc-gerador-danfse/tree/8d79e6b2f7fad6375340afcb51c85ed370c64a14) é um renderizador Go. Exponha **somente** os serviços necessários por HTTPS, com autenticação, controle de acesso e de taxa. GitHub/Pages, localhost do operador e uma página de Swagger não são endereços de motor.
2. No **projeto Supabase dedicado → Edge Functions → Secrets**, configure as bases HTTPS autorizadas (um prefixo de proxy é aceito; a função acrescenta a rota). Não coloque URLs internas, tokens ou certificados em `VITE_*` ou no repositório. A conta usa o gateway autenticado: ele valida o JWT, a confirmação de e-mail e a permissão/cota, sem gravar o conteúdo da operação. O upstream recebe o conteúdo somente ao calcular/renderizar.

   | Serviço | Configuração no servidor | GET de diagnóstico após a atualização |
   |---|---|---|
   | Regime regular | `RTC_REGULAR_URL` | `/api/calculadora/dados-abertos/versao` |
   | Simples Nacional | `RTC_SIMPLE_URL` | `/api/versao` |
   | Base da NFS-e | `RTC_BASE_URL` se for outra instalação; na ausência usa `RTC_REGULAR_URL` | `/api/calculadora/dados-abertos/versao` |
   | Gerador DANFSe | `RTC_DANFSE_URL` | `/health/ready` |

   `RTC_API_TOKEN` e `DANFSE_API_TOKEN` são Bearer opcionais destinados exclusivamente às instâncias correspondentes. O navegador não escolhe destinos. Redirecionamentos não são seguidos.
3. Republique `supabase/functions/eleao-api/index.ts` no **mesmo projeto do frontend**, mantendo a verificação de JWT (CLI: `supabase functions deploy eleao-api --project-ref zfmmcnuyegrjmeurbgbl`, a partir da raiz e com identidade administrativa autorizada). Nenhuma nova migração ou chave publicável é necessária. A versão nova também mantém a remoção da ação paga `assistant` e o encaminhamento do aviso de dados simulados somente quando retornado pelo motor.
4. Entre com uma conta aprovada. Em **Calculadora RTC → Motor RTC / Base da NFS-e** ou **Notas de serviço → Gerar DANFSe**, use **Verificar conexão do serviço**. Verifica uma resposta de versão/prontidão reconhecida, sem enviar operação/XML. Não atesta homologação ou sucesso de todos os cálculos. Faça em seguida uma operação de teste autorizada, verificando estados e avisos por item. A verificação com upstream consome uma das 40 consultas diárias; com configuração ausente/inválida, a versão nova verifica a conta sem debitar cota.

**Leitura dos avisos:** “ainda não foi conectado” → cadastrar a URL; “recusou o acesso do e-Leão” → verificar credencial do upstream, não a senha do contribuinte; “não oferece esta rota” → conferir prefixo e contrato; tempo limite/sem resposta → verificar DNS, TLS, disponibilidade e acesso de rede **a partir do gateway**. Erros de sessão, campos e cota permanecem distintos. Se a verificação não for reconhecida, confirme o deploy de `eleao-api`: o frontend entende a mensagem de serviço não configurado da v3, mas não pode acrescentar rotas a um backend antigo.

**Base pública e piloto oficial:** as [tabelas da revisão fixada](CENARIOS.md#consulta-de-ncm-e-nbs-sem-motor) não precisam dos segredos RTC. Separadamente, a ação autenticada `reference-version` permite um único GET a `https://piloto-cbs.tributos.gov.br/servico/calculadora-consumo/api/calculadora/dados-abertos/versao`, exatamente o endereço de comparação da [configuração offline oficial](https://github.com/ReceitaFederal/calculadora-rtc-regime-regular/blob/150cccbe414d4a5edea703e4f7a424af5aa222c7/src/main/resources/application-offline.yml). Não leva corpo, token, código fiscal ou dados da conta, não segue redirecionamentos e não substitui tabelas. Depende de egress HTTPS, de uma vaga na cota e da disponibilidade do piloto. Não use o piloto como destino automático de operações ou XML; não há acesso direto a bancos internos da Receita nem a cadastros protegidos.

**A emissão via API está bloqueada por desenho.** `action=emit` devolve HTTP 501. Para a ativar, é necessário construir e revisar integração SEFIN/ente autorizado, autenticação mútua, credenciamento, assinatura/verificação XMLDSig, certificado armazenado em cofre KMS/vault com consentimento e vínculo de titularidade, Idempotência, contingência/cancelamento/substituição, homologação e auditoria LGPD. Não troque o bloqueio pelo renderer DANFSe. Até essa integração certificada existir, acesse o emissor autorizado e importe o XML efetivamente autorizado para gerar a representação auxiliar.

## Assistente generativo local

No workspace autenticado, **abrir o Assistente fiscal** prepara a IA automaticamente. O início do site e as outras ferramentas não carregam o modelo. Durante o carregamento, a tela mostra a barra e a porcentagem; a conversa já fica disponível. Em **Opções da conversa → Usar só os guias**, é possível interromper o download. O motor [wllama](https://github.com/ngxson/wllama) executa llama.cpp em Web Worker na CPU, inclusive em Pages sem WebGPU ou isolamento entre origens. O JS e os WASMs (inclusive a versão de compatibilidade) vêm do próprio build. Os pesos não entram no Git nem no bundle: [Qwen3-0.6B, Q4_K_M, revisão fixa](https://huggingface.co/unsloth/Qwen3-0.6B-GGUF/tree/50968a4468ef4233ed78cd7c3de230dd1d61a56b), modelo-base [Qwen3-0.6B](https://huggingface.co/Qwen/Qwen3-0.6B), licença Apache-2.0. São 396.705.472 bytes de pesos, além do runtime e da memória de inferência. Os avisos de licença do [wllama](../public/licenses/wllama-MIT.txt) e do [llama.cpp](../public/licenses/llama-cpp-MIT.txt) acompanham os arquivos estáticos. A inferência não usa cota do gateway, cartão nem conta de provedor de IA; há consumo local de dados, memória e CPU.

É necessário HTTPS (ou loopback de desenvolvimento), navegador recente com WebAssembly, Worker e armazenamento privado da origem. Se os pesos não estiverem em cache, há acesso ao Hugging Face e ao seu CDN **apenas para os pesos/metadados**. O provedor do download pode ver o IP, não a pergunta ou os guias. Armazenamento limitado, janela privada, rede bloqueada e dispositivos com pouca memória podem impedir o carregamento. A consulta textual é identificada como tal e continua disponível. Sair da tela ou escolher **Usar só os guias** libera o worker. A preferência por guias fica no armazenamento local do navegador, quando disponível. **Opções da conversa → Apagar apenas o modelo em cache** remove os pesos e seleciona só guias para não baixá-los novamente sem intenção; **Voltar a usar a IA** retoma o modo automático. O navegador também pode descartar o cache.

O contexto usa os guias disponíveis à conta, a referência de alíquotas da calculadora e as definições do art. 1º da LC 214/2025. Uma pergunta igual à de um guia recebe imediatamente o texto revisado. Ao perguntar o que significa IBS, CBS ou ambos, a intenção e as siglas são identificadas **antes** da busca por palavras. O assistente usa uma pergunta equivalente da curadoria, se houver; na ausência dela, responde com a definição legal das siglas solicitadas. Essa resposta não entra na fila de geração.

A referência numérica de transição exige um pedido de percentuais em contexto compatível, não apenas a menção a IBS/CBS. Se o usuário especificar outro aspecto e só as siglas coincidirem, o assistente informa que não encontrou um guia para confirmá-lo. As referências embutidas não recebem votos nem exigem uma migração para funcionar. Para alinhar também o artigo de comparação na biblioteca autenticada, a migração `20261118001400_ibs_cbs_definition.sql` atualiza apenas o registro original, sem sobrescrever a curadoria.

Nas perguntas livres, a fonte encontrada aparece na conversa antes da explicação; enquanto a IA carrega, os guias já funcionam e a última pergunta livre pode ser explicada ao ficar pronta. Se a pesquisa textual não basta, o modelo pode selecionar um guia de um catálogo limitado. O stream sinaliza leitura e redação, mas nenhum fragmento gerado é mostrado antes das verificações sobre a resposta completa. Após 35 segundos sem progresso ou 90 segundos por geração, o worker é encerrado, a consulta aos guias permanece e o modelo é preparado para a próxima pergunta, sem repetir a inferência anterior. Não é preciso cancelar para perguntar de novo: uma nova pergunta livre tem prioridade sobre a explicação em andamento, sem ocupar simultaneamente o mesmo worker. Fontes exibidas vêm da aplicação, não de URLs geradas. O guia local é educativo e não atesta uma atualização em tempo real. A pesquisa online é identificada separadamente. Conversas não ficam no histórico; votar num guia do banco envia apenas a avaliação desse artigo. Em respostas com percentuais numéricos, a interface exige frases do texto revisado em vez de aceitar um número só porque ele também aparece no guia. Essa verificação não garante a correção de toda afirmação. Falhas, cancelamento ou texto que não passa pela validação não são rotulados como resposta de IA.

### Pesquisa online do assistente

- **Experiência:** habilitada por padrão para contas aprovadas. A caixa **Pesquisar na internet · fontes oficiais** junto à pergunta mostra os termos que serão enviados. Desmarcá-la não desliga a IA local; **Usar só os guias** desliga ambos. Não há envio ao abrir a tela nem enquanto se digita.
- **O que é consultado:** a ação `official-search` pesquisa a seção 1 do [Diário Oficial da União](https://www.in.gov.br/consulta) (primeira página desde 2000, [contrato do portal usado pelo Ro-dou](https://github.com/gestaogovbr/Ro-dou/blob/4ebffbacd474eabb96469d3a78463421e9bb9163/src/hooks/dou_hook.py)) e ementas no [LexML](https://www.lexml.gov.br/busca/SRU) (SRU/Dublin Core, legislação federal). Na mesma consulta, lê e filtra o [feed de últimas notícias da Receita](https://www.gov.br/receitafederal/pt-br/assuntos/noticias/ultimas-noticias/RSS). Não é a busca no feed diário do site nem uma pesquisa irrestrita em toda a web. Os três acessos são HTTPS, paralelos, limitados em tempo e tamanho, sem seguir redirecionamentos. Nenhum link retornado é buscado pelo servidor.
- **O que fundamenta a resposta:** até três resultados de órgãos oficiais passam por validação de origem e pertinência. O chat distingue **Fonte da resposta** de **Resultado relacionado** e mostra título, órgão, link original, trecho, data indicada pela fonte quando disponível e horário da consulta. O modelo local lê os trechos e seleciona o que responde à pergunta, ou indica que nenhum basta. A aplicação valida o índice e reproduz o texto do resultado junto ao link correspondente, em vez de aceitar percentuais ou citações escritos pelo modelo. Um índice inválido ou texto inventado não vira citação. Uma ementa, notícia ou data de publicação não comprova vigência, nem substitui ler o ato integral. A pesquisa não altera a calculadora ou a curadoria. Uma definição ou FAQ já resolvida continua aparecendo imediatamente e não é reescrita pelos resultados da busca.
- **Limites e privacidade:** envia-se uma seleção fechada de termos fiscais e, se houver, o ano, não o texto da pergunta, histórico, CPF/CNPJ, documento ou operação. Sem termo reconhecido não há envio. O DOU e o LexML recebem os termos; a leitura do feed não os transmite à Receita. As respostas são efêmeras. Buscas completas idênticas podem ser reutilizadas por cinco minutos na conversa; a interface indica esse reuso. Só a preferência fica no armazenamento local. A cota de **40 pesquisas por conta/dia** é separada da do RTC; o banco guarda apenas conta, dia e contagem. Não registrar corpos de requisições e respostas nos logs de operação.
- **Publicação:** aplicar `supabase/migrations/20261118001500_research_quota.sql` no projeto dedicado, depois fazer `supabase functions deploy eleao-api --project-ref zfmmcnuyegrjmeurbgbl` a partir da raiz (inclui `_shared/research.ts`, `research.ts` e o `deno.json` da função), mantendo verificação de JWT. Publicar o frontend em Pages. **Sem chave nova, sem serviço de IA externo e sem alterar os segredos RTC.** Pages não implanta a migração nem a função. Permitir saída HTTPS da Edge para `www.in.gov.br`, `www.lexml.gov.br` e `www.gov.br`.
- **Verificação após deploy:** com conta aprovada, perguntar, por exemplo, sobre crédito de CBS. Conferir os termos, o horário e abrir a fonte para verificar o contexto. Buscar um termo muito específico pode não produzir resultado. Fonte parcial, pesquisa vazia, limite da conta e indisponibilidade são indicados sem apresentar o guia local como confirmação pela internet. Desmarcar a pesquisa e repetir não deve gerar uma chamada `official-search`.

## Referências da estimativa rápida

A fonte é a [LC 214/2025, texto consolidado](https://www.planalto.gov.br/ccivil_03/leis/lcp/lcp214compilado.htm), revisão das referências em 18/11/2026. Na regra geral sem redução: em 2026, IBS estadual 0,1% (art. 343) e CBS 0,9% (art. 346), observados o art. 348, as reduções, exceções e condições de dispensa de recolhimento. Em 2027–28, IBS total de 0,1% (0,05% estadual + 0,05% municipal, art. 344). Não extrapolar esses números para outros tributos, anos ou enquadramentos. Não há sugestão numérica para IS, Simples Nacional, ou CBS após 2026. A aplicação da referência é explícita por campo e fica identificada na simulação salva; a legislação não é sincronizada automaticamente. Revise `src/lib/rateReferences.ts` e seus testes antes de mudar as vigências.

Migrações em `supabase/migrations/` são só de domínio `eleao_*`, requerem revisão antes de reaplicar num projeto; confirme `public.eleao_*`, políticas, guias publicados, grants e chaves antes de executar. Adapte primeiro o seed/editor se ele divergir dos guias já publicados. Não deixe clientes anon consultarem os artigos da base sem configurar política explícita. Edge Function, motores externos, renderização final DANFSe, SMTP, IA, cadastro e emissão oficial ainda não foram testados em produção.

## Privacidade e operação

O cliente envia tokens apenas ao Supabase/Edge Function, usa chave publicável e não insere certificados fiscais no histórico. As exportações são locais, o CSV neutraliza fórmulas, e comentários são privados/opt-in. Configure política de privacidade, encarregado/canal LGPD, retenção/descarte, backups, logs mínimos, alerta de abuso e política de incidentes antes de produção. Não rotule o painel gerencial como apuração contabilística do contribuinte. Atualize e teste cada versão upstream, catálogo, taxa e vigência antes de mudar qualquer taxonomia exibida.

O roteiro de revisão é orientativo e não substitui apuração nem determina obrigações. ## Consulta diária de fontes oficiais

O workflow Pages inclui uma execução agendada diária às 09:17 UTC, além de push e acionamento manual. Depois do build, `scripts/official_updates.py` consulta dois feeds RSS da Receita Federal (notícias gerais e reforma tributária) e grava `dist/official-updates.json` para a seção de notícias. O conteúdo é limitado a títulos, datas e links HTTPS do domínio oficial permitido; não executa conteúdo remoto nem atualiza regras fiscais ou o banco automaticamente. A interface indica falhas por fonte e avisa quando a última tentativa tem mais de 48 horas. Se o workflow não rodar ou o deploy falhar, o site pode permanecer antigo; monitore a execução em Actions. Serviços externos podem alterar feeds, formatos ou URLs. O agendamento do GitHub não garante horário exato e pode ser desativado em repositórios inativos; verifique também o status do Pages e de Actions.

A consulta a dois feeds **não cobre todas as leis, todos os órgãos, as jurisdições locais, todas as ferramentas nem todos os conteúdos existentes**. O FAQ e as regras de cálculo precisam de revisão técnica humana, comparação com fontes, testes e publicação; a calculadora externa apontada pelo gateway também requer manutenção independente. Uma notícia não equivale a texto legal consolidado. Confira sempre normas, vigência e exceções diretamente. `python3 -m unittest discover -s tests -p 'test_*.py'` testa a extração e falhas sem rede.

## Convites manuais sem domínio de e-mail

O fluxo novo não usa e-mail para criar conta: visitantes enviam nome e e-mail declarado, o proprietário confere a identidade fora do sistema e gera no painel um link secreto de uso único com validade de 48 horas. Um novo link invalida o anterior. A pessoa define a própria senha no link. A validação é de posse do link, **não comprova a propriedade do e-mail**; o proprietário deve confirmar a identidade por um canal confiável antes de emitir. O link deve ser tratado como senha e não pode ser publicado ou enviado a terceiros.

No projeto dedicado foram instaladas as migrações 004 a 006 e a função `eleao-invite` com `verify_jwt=false`, e o cadastro público direto no Supabase Auth foi desabilitado. O frontend ainda deve ser publicado de forma coordenada. A função usa `SUPABASE_SERVICE_ROLE_KEY` apenas no servidor; não colocá-la no frontend. Seu RPC reserva o convite de forma atômica e só ativa a conta após criação bem-sucedida. Se uma falha ocorrer após a reserva, ela fica `processing` para análise administrativa, em vez de reutilização insegura. Antes de lançar, teste geração, cancelamento, reemissão, expiração, consumo concorrente e falhas com duas contas reais em ambiente de teste. A conta existente do proprietário deve ser validada antes de desabilitar o cadastro. O endpoint de solicitação tem um limite global simples, mas precisa de proteção adicional antiabuso (CAPTCHA/WAF e limites por IP) antes de uso público; privacidade e retenção dos pedidos também precisam de política. A recuperação automática de senha ainda depende de SMTP funcional e verificação de domínio; até lá é necessária operação manual segura. Não confundir aprovação manual com verificação de caixa postal.

A verificação remota criou uma conta temporária por convite, confirmou autenticação e rejeição do reuso; a conta e a solicitação de teste foram apagadas. Foram confirmados RLS e grants restritos do fluxo. O teste não confirma login da conta pessoal do proprietário. A mudança 007 adiciona bloqueio transacional ao limite global; ela não substitui limitação por IP nem CAPTCHA.

Para os testes remotos foi habilitada a extensão `pg_net`, sem agendamentos automáticos; os testes usaram dados temporários e foram limpos. As migrações executadas pelo conector receberam versões registradas pelo Supabase diferentes dos prefixos locais; reconcilie o histórico antes de usar `supabase db push` para evitar reaplicação.

## Recuperação manual e mitigação de abuso (implantação coordenada)

As migrações 009 e 010, a função `eleao-recovery` e a interface correspondente foram publicadas no projeto dedicado. Para membros ativos, o proprietário pode emitir um link secreto de uso único, válido por uma hora, e entregá-lo após verificar a identidade por outro canal. Um novo link invalida links anteriores ainda não usados. O proprietário não vê a senha. Esta recuperação **não atende a conta do proprietário**: mantenha um procedimento independente e seguro de recuperação do acesso ao Supabase/conta administrativa. Uma falha após reserva exige análise e novo link. Se a alteração da senha ocorrer mas a finalização falhar, sessões antigas podem continuar ativas; trate como incidente. Mesmo com a finalização bem-sucedida, tokens de acesso já emitidos podem continuar válidos até expirarem. Em teste remoto temporário, recuperação e login com a nova senha retornaram 200, reuso retornou 400 e as sessões anteriores foram excluídas; a conta e dados do teste foram removidos.

A prova de trabalho SHA-256 vincula nome, e-mail e horário e aumenta o custo de solicitações automatizadas. A migração 011 foi aplicada após a publicação e revogou o acesso público ao RPC legado `eleao_request_access`. Mais tarde, a migração 013 também revogou o acesso público direto ao RPC de prova de trabalho, exigindo a verificação Turnstile pelo servidor. O limite global continua sujeito a esgotamento e essas medidas não substituem WAF, limite por IP, monitoramento ou política de retenção.

## Turnstile gratuito para solicitações (ativo)

A integração usa Cloudflare Turnstile no formulário de solicitação e valida o token **no servidor** com Siteverify, conferindo sucesso, hostname `ademirvarjao.github.io` e ação `solicitar_acesso`. Mantém também a prova de trabalho. Não usar as chaves públicas de teste em produção: as chaves secretas de teste são recusadas pela função. Veja [plano gratuito](https://developers.cloudflare.com/turnstile/plans/) e [validação no servidor](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/). É possível cadastrar o hostname do GitHub Pages sem comprar um domínio; não é necessário alterar o DNS. O Turnstile não substitui WAF ou limites por IP, nem garante que todo pedido é legítimo; a aprovação permanece exclusiva do proprietário.

### Configuração de produção (pelo responsável pelas contas)

1. Criar conta gratuita na Cloudflare, abrir **Turnstile** e criar um widget **Managed** para o hostname `ademirvarjao.github.io` (sem `https://` e sem caminho). Não usar chaves de teste. Confirmar no painel se esse hostname é aceito.
2. No repositório GitHub, em **Settings → Secrets and variables → Actions → Variables**, criar a variável `VITE_TURNSTILE_SITE_KEY` com a *site key*, que é pública. O workflow a incorpora no build. Não colocar a chave secreta em `VITE_*`, no repositório ou em mensagens.
3. No painel do projeto Supabase dedicado, em **Edge Functions → Secrets**, adicionar `TURNSTILE_SECRET_KEY` com a chave secreta real do widget. O valor não deve ser compartilhado no chat. O projeto Conversor não deve ser alterado.
4. A migração equivalente a `20261118001200_turnstile_verified.sql` e a função `eleao-request` com `verify_jwt=false` já foram instaladas no projeto dedicado pelo conector, com versão remota diferente do prefixo local. A função depende de `SUPABASE_URL` e `SUPABASE_SERVICE_ROLE_KEY` do ambiente de Edge Functions. O Siteverify rejeitou um token inválido, e um teste real do proprietário produziu uma solicitação pendente e um token consumido no mesmo instante antes da ativação. Conferir erros sem registrar senhas, tokens ou segredos. Não executar `supabase db push` sem reconciliar as versões remotas.
5. A interface foi publicada com a variável de build configurada. O proprietário enviou um pedido de teste usando o widget real, e o pedido foi encontrado no banco com registro de consumo de CAPTCHA no mesmo instante; o pedido de teste foi removido. As falhas, ação e hostname incorretos e reuso também são cobertos por testes locais; nem todos os cenários foram reproduzidos com tokens reais em produção.
6. A migração equivalente a `20261118001300_turnstile_enforcement.sql` foi aplicada no projeto dedicado. Foi confirmado que `anon` e `authenticated` não podem executar diretamente `eleao_request_access_pow` nem `eleao_request_access_verified`; somente `service_role` pode executar a segunda. Após a virada, um teste interno confirmou que essa função ainda consegue registrar uma solicitação com prova válida, e uma tentativa anônima direta foi rejeitada. O pedido e os dados internos do teste foram removidos. Um novo desafio real após a virada não foi exercitado. Clientes antigos em cache precisam recarregar a página.

Se a chave estiver ausente, o serviço da Cloudflare falhar ou o widget não carregar depois da virada, a solicitação é bloqueada, sem fallback inseguro. Planejar reversão com cautela: restaurar a permissão pública de `eleao_request_access_pow` remove a obrigatoriedade do CAPTCHA para todos até nova ativação. Os tokens validados são armazenados apenas como hash por ao menos 15 minutos e limpos quando há novas solicitações; o limite global pode ser esgotado por tráfego malicioso, e redes ou navegadores que bloqueiem scripts externos podem não conseguir enviar o formulário.
